## Goal

Give a workflow its own working directory so agents can run concurrently without
interfering with one another or with the user's live checkout.

There are two supported shapes:

1. **Managed worktree:** ctrlyoke creates a run-scoped worktree and branch, runs
   the workflow there, commits any resulting changes, removes the directory, and
   leaves the branch for review.
2. **Named worktree:** ctrlyoke targets a persistent worktree the user already
   owns, or creates it on first use. It never commits, merges, or removes that
   worktree automatically.

Existing non-worktree workflows remain supported and may continue running in
parallel exactly as they do today. Choosing worktree mode opts into stronger
directory isolation; it does not globally serialize ordinary workflows.

### The result lives in the branch

Git worktrees share the object store and refs. A managed branch remains visible
from the initiating checkout after its linked directory is removed:

```text
git diff <base-commit>...ctrlyoke/ui-refactor/run-2026-07-27T14-02-11-123Z
```

This avoids the unusable middle state where the agent worked in an ephemeral
directory but left no reviewable result behind.

### Non-goals for the first release

- A workflow does not switch worktrees between steps.
- A worktree does not span several repositories.
- ctrlyoke does not silently expose other repositories or non-repository
  workspace folders to a worktree run.
- Managed-worktree history does not provide undo after the worktree directory has
  been removed. ctrlyoke's only undo mechanism is filesystem content restore, so
  there is no git-based fallback. The captured diff and its attribution remain
  viewable.
- ctrlyoke does not automatically rebase, pull, or synchronize named branches.

## Verified Current Baseline (2026-08-10)

- There is no workflow `worktree` schema/type/runtime implementation yet.
- `IntegrationFactory.createForExecution(harness)` constructs integrations against
  one long-lived `PlatformAdapter`; `CliIntegration` and its composed helpers read
  workspace roots from that adapter. The execution workspace must therefore enter
  at factory construction, not as a late spawn-only cwd override.
- `WorkflowExecutionContext` currently carries `workspaceFolderPath` plus
  `namedWorkspaceRoots`; process output, snapshots, scripts, and history all reuse
  that primary path with different semantics.
- `WorkingFileManager.updateWorkingFileDirect()` reconstructs root `_runtime` from
  queue state. A disk-only worktree block would be lost unless preservation is
  added deliberately.
- `UndoRedoCoordinator` currently accepts a webview-supplied `workspacePath` and
  resolves multi-root paths against the current VS Code window, so worktree undo
  requires a backend-addressed root lookup and guard.
- `WorkflowLockManager` has owner-token/PID/30-second-heartbeat safety, while the
  five-second heartbeat interval still lives in `WorkflowInstance`. These are the
  primitives to extract; the lineage runner lock itself remains separate.
- Execution integrations can retain PTYs, session-activity watchers, provider
  artifacts, and per-execution sidecars. Worktree settlement must explicitly stop
  all of them before commit/removal or lease release.
- `schemas/workflow-schema.json` is authoritative and
  `schemas/workflow-schema.yaml` is generated by `npm run generate-schema`.

## Git Worktree Model

A linked checkout of the same repository at a different path. Each worktree has
its own checked-out branch and working directory while sharing Git objects and
refs:

```text
C:\dev\FlightPath\                       branch: main
C:\dev\FlightPath.worktrees\ui-work\     branch: ui-work
C:\dev\FlightPath.worktrees\backend\     branch: backend
```

The harness process launches with its cwd in the selected worktree. From the
agent's perspective it is an ordinary repository checkout.

Two worktrees cannot check out the same branch simultaneously. Discovery and
errors must surface the existing checkout path rather than forwarding Git's raw
"already checked out" failure.

## Worktree Location

### Default layout

```text
<parentOf(sourceCheckoutRoot)>/<repoName>.worktrees/<safe-run-id>/
```

Example:

```text
C:\dev\FlightPath
C:\dev\FlightPath.worktrees\ui-refactor-a13f9082
```

The physical directory name is generated independently from the Git branch
name. It uses a readable, length-bounded slug plus a stable hash, so branch
slashes, long workflow names, collisions, and path traversal cannot affect
filesystem placement.

Use one shared name helper: lowercase an ASCII-safe slug, collapse other runs to
`-`, trim separators, fall back to `workflow`, and cap it at 40 characters. Append
the first 12 hex characters of SHA-256 over the canonical common-directory
identity plus `workflowKey/runRef` (managed) or the exact local branch ref (named).
If an existing candidate does not match the expected ownership/identity record,
fail as a collision rather than lengthening or reusing it. Managed branch names
are `ctrlyoke/<slug>/<runRef>` and still pass `git check-ref-format --branch`.

### Resolution order

1. User-scope `worktrees.root`, when configured. Accept an absolute path or a
   path beginning with `~`. An invalid or unwritable explicit value is a hard
   error; do not silently ignore the user's choice.
2. `<parentOf(sourceCheckoutRoot)>/<repoName>.worktrees/`.
3. `~/.ctrlyoke/worktrees/<repo-identity>/`, but only when creation of the
   default sibling root fails for a real permission/filesystem reason.

`repo-identity` is a readable repository slug plus a hash of the canonical Git
common-directory identity. Flattening a path alone is insufficient because
different paths can flatten to the same string.

Root creation is the writability probe: attempt to create the directory and
fall back on an actual permission/filesystem failure. Do not rely only on
`fs.access(W_OK)`.

### Placement guards

After resolving symlinks through the nearest existing ancestor:

- Reject any resolved root equal to or contained within the source checkout.
- Reject any resolved root contained within any discovered worktree.
- Reject a worktree path that escapes its resolved worktree root.

Do not add an arbitrary path-length warning in the first release. Keep generated
directory names bounded and surface the actual Git/filesystem error if the host's
path policy rejects a path.

The worktree root setting is user-controlled only. Workspace-scope configuration
must not be able to redirect checkout creation to an arbitrary external
directory.

### Why worktrees are not nested under `.ctrlyoke/`

Nesting a worktree under the repository breaks or weakens several existing
systems:

| Problem                                                                               | Current evidence                        |
| ------------------------------------------------------------------------------------- | --------------------------------------- |
| TypeScript sees a second `src/**/*.ts` outside `rootDir` and fails with TS6059.       | `tsconfig.json`                         |
| Pure containment attributes nested worktree files to the source checkout.             | `src/utils/WorkspaceRepoDiscovery.ts`   |
| Snapshot walking excludes `.ctrlyoke`, so worktree changes disappear.                 | `src/utils/WorkspaceSnapshotService.ts` |
| `.ctrlyoke/` is not wholesale ignored or runtime-only.                                | `.gitignore`, `WorkspaceInitializer.ts` |
| `git clean -xdf` can destroy the nested checkout and orphan Git administration state. | Git behavior                            |
| Search, watchers, linting, tests, and bundlers see a second repository copy.          | Tool behavior                           |

Sibling placement is therefore a correctness requirement, not only a
convention.

### Fresh-checkout consequences

A new managed worktree does not contain ignored files such as `node_modules`,
local `.env` files, generated assets, or initialized caches. Managed mode is not
considered ready until it supports a setup command that runs once after
creation and before the first workflow step.

Setup failure marks the worktree blocked and leaves the directory in place for
inspection. ctrlyoke must never delete a directory after a failed setup if that
directory contains uncommitted changes. Persist the blocked state and release
the execution lease and lineage runner lock so recovery is possible, and
transition the workflow through `WorkflowStateMachine` rather than inventing a
parallel run status. Reuse the extracted script execution/reporting
infrastructure with the worktree as cwd rather than adding a second shell runner.

### Seeding `.ctrlyoke/.gitignore` in the worktree

A fresh worktree usually has **no `.ctrlyoke/.gitignore`**, and without it managed
auto-commit sweeps ctrlyoke's own runtime files into the user's branch.

`WorkspaceInitializer.ensureGitignore` only ever manages `<ctrlyokeDir>/.gitignore`;
it never writes to the repository root. That generated file lists `.gitignore`
among its own entries, so it ignores itself, stays
untracked, and is absent from any fresh checkout. Meanwhile the role table below
routes temp prompt files, hook artifacts, and notification directories to
`<executionRoot>/.ctrlyoke/`. Those paths are then non-ignored, and managed
finalization commits "all tracked/untracked, non-ignored changes."

This repository is incidentally immune because `.ctrlyoke/.gitignore` was
force-added here (the root `.gitignore` also duplicates several entries), so the
failure will not reproduce locally. A typical user repository has neither
protection.

**Requirement:** call `WorkspaceInitializer.initializeIfNeeded(executionRoot)`
immediately after creating or attaching a worktree and before running `setup`, so
the ignore file exists before the first harness write. This is idempotent and
reuses existing code. Auto-commit must additionally verify that no path under
`.ctrlyoke/` runtime directories is staged, and fail finalization as `blocked`
rather than committing them if the guard trips.

The runtime-path list must be exported from the same constant source consumed by
`WorkspaceInitializer`; the commit guard must not duplicate the entries. Perform
the guard before changing the index where possible, and include already-tracked
runtime paths. Authored `.ctrlyoke` content (`agents/`, `skills/`, `scripts/`,
`templates/`, `mcp/`, settings, and workflow definitions) remains committable.

## Execution Workspace and Root Separation

The current code uses "workspace root" for state storage, process cwd, prompt
resolution, script security, snapshots, MCP routing, and multi-root access.
Worktree support makes those roles distinct.

Use one immutable execution-workspace contract rather than threading an
optional cwd through individual calls:

```typescript
interface ExecutionWorkspace {
  /** Where ctrlyoke stores .ctrlyoke/.runs, history, queue state, and locks. */
  stateRoot: string;

  /** The cwd used by the harness, scripts, conditions, and temp prompt files. */
  executionRoot: string;

  /** Canonical Git toplevel from which a linked checkout is created. */
  sourceCheckoutRoot?: string;

  /** Canonical Git toplevel of the checkout in which execution occurs. */
  executionCheckoutRoot?: string;

  /** Trusted project roots as seen by execution, with repo-owned roots remapped. */
  workspaceRoots: string[];

  /** Name/path pairs used by multi-root references and snapshots, also remapped. */
  namedWorkspaceRoots: ResolverWorkspaceFolder[];

  /** External roots approved against stateRoot's trust identity. */
  approvedExternalRoots: string[];
}
```

When no worktree is active:

```text
executionRoot = stateRoot
workspaceRoots = platform.getWorkspaceRoots()
namedWorkspaceRoots = platform.getNamedWorkspaceRoots()
```

That no-worktree case must remain behaviorally identical to today.

### Mapping a checkout into a worktree

For a source root contained in the repository:

```text
mappedRoot = join(worktreeToplevel, relative(sourceCheckoutRoot, sourceRoot))
```

Every named workspace root belonging to the repository is mapped this way.

`sourceCheckoutRoot` and `executionCheckoutRoot` always mean Git toplevels.
They are not necessarily the process cwd. When `stateRoot` is inside the sole
repository, preserve its relative location and use the mapped equivalent as
`executionRoot`; this keeps a workspace opened at a monorepo subdirectory from
silently changing cwd to the repository root.

`stateRoot` can legitimately be outside the repository, for example when it is
the directory containing a saved `.code-workspace` file. In that case:

- `stateRoot` remains unchanged for ctrlyoke state.
- `executionRoot` is the worktree toplevel.
- Every named repository root is remapped into the worktree.

This avoids `relative(repoRoot, stateRoot)` producing an escaping `..` path.
In worktree mode, `workspaceRoots` contains only `executionRoot` and remapped
repository roots. It must not retain an unmapped source-checkout/state path.

The authored `sourceDefinitionPath` remains a state-side persistence identity,
but prompt reference expansion receives an execution-side semantic path. Map it
lexically into the worktree when it is inside the repository, even if the authored
workflow itself is untracked and therefore absent from the checkout. If the
authored definition is outside the repository, reject leading `./` or `../`
references in worktree mode because they cannot be mapped without exposing a live
state directory; ordinary workspace-relative references continue to resolve from
`executionRoot` and the remapped named roots.

### Role assignment

| Role                                                      | Root                                |
| --------------------------------------------------------- | ----------------------------------- |
| Harness process cwd                                       | execution                           |
| Temp prompt and harness-config files                      | execution                           |
| Relative `@` references and prompt rendering              | execution plus remapped named roots |
| Claude/Qwen session-log project lookup                    | execution                           |
| Provider hooks, notifications, and workspace-local config | execution                           |
| `preCondition`, `endCondition`, and script cwd            | execution                           |
| Script-path security allowlist                            | execution plus user home scripts    |
| Snapshot capture and per-repo discovery                   | execution plus remapped named roots |
| Harness `--add-dir` workspace arguments                   | remapped execution workspace roots  |
| `endCondition` / `preCondition` script **files**          | execution plus user home scripts    |
| Workspace agent and skill **definition files**            | execution (see below)               |
| User/bundled agent and skill definitions                  | user/extension locations            |
| Workflow, prompt, and template discovery                  | state                               |
| MCP `CTRLYOKE_WORKSPACE`                                  | state                               |
| MCP `CTRLYOKE_WORKING_FILE`                               | state working-file path             |
| Run storage, lineage, history, runner locks               | state                               |

`CliMcpConfigGenerator` therefore needs separate locations for where it writes
its temporary config and which state root it exports to the MCP server.

Existing approved-external-root decisions are keyed by the state workspace
identity. Resolve them once for `stateRoot` and carry them in
`ExecutionWorkspace`; do not recompute trust using the ephemeral worktree path.
Explicit external roots may remain passthrough roots, but worktree preflight must
reject any approved/additional root that equals, contains, or is contained by the
source checkout. That prevents an old trust decision or CLI `--add-dir` from
silently granting write access back into the live checkout. The UI should state
that other explicitly approved external roots are outside worktree isolation.

`EndConditionEvaluator` must accept the execution workspace as both cwd and an
allowed script root. Merely changing cwd would cause its existing security check
to reject scripts inside the sibling worktree.

### ctrlyoke asset discovery

The split above assigns where the harness _runs_. It must also state where
user-authored ctrlyoke assets are _found_, because the two answers differ and the
difference is currently accidental rather than chosen.

**Decision for the first release:** authored workflow/template discovery remains
state-side; scripts and workspace-scoped agents/skills resolve from the execution
workspace. User-scoped and bundled agents/skills remain unchanged.

This refactor belongs in Phase 1. `AgentExpander` and `SkillExpander` currently
accept a root but convert it back to a live VS Code `WorkspaceFolder`, falling back
to the first open source folder. That would silently defeat the root split.
Parameterize `AgentDiscovery` and `SkillDiscovery` with a plain root contract and
verify `SkillDiscovery.findGitRoot()` in a linked worktree. This is also required
because skill expansion emits a path for the harness to read; pointing that path
at `stateRoot` would either fail sandbox access or require exposing the live source
checkout through `--add-dir`.

The consequence is intentional and consistent with Git semantics: uncommitted
workspace-local agent/skill changes are not available in a fresh worktree. Report
an actionable preflight diagnostic when a configured workspace asset exists only
in the source checkout. Scripts follow execution because they validate the branch
content the agent just changed.

### Integration lifecycle

`IntegrationFactory.createForExecution()` receives the immutable
`ExecutionWorkspace`. `CliIntegration` exposes explicit state/execution accessors
instead of changing the meaning of `getWorkspaceRoot()` invisibly.

An integration retained for PTY injection or post-completion session activity
is reusable only when the next execution has the same execution-workspace
identity. Managed-run finalization must dispose retained integrations and
session watchers before committing or removing their directory.

## Workspace Eligibility

A worktree checks out exactly one repository. The first release uses a strict,
structural rule:

1. Discover repositories from all named workspace roots.
2. Require exactly one distinct repository.
3. Require every named workspace root to be contained within that repository.
4. Permit `stateRoot` itself to sit outside the repository solely as ctrlyoke
   state storage.

**A multi-root workspace is not disqualified by being multi-root.** A monorepo
opened as several workspace folders passes: `discoverRepos` collapses roots sharing
a Git toplevel to one entry, every root is contained in that repository, and each
one remaps into the worktree independently. What is refused is _multiple
repositories_, and roots that fall outside the sole repository.

Refuse worktree mode when:

- No Git repository is present.
- More than one repository is present.
- A named root is not inside the sole repository.

This intentionally rejects non-repository passthrough roots. Passing those
roots to `--add-dir` would give the agent write access to live files and create
the same silent partial-isolation problem as worktreeing only one repository in
a multi-repo workspace.

Deferred designs:

- Explicit read-only passthrough roots.
- `worktree: { repo: "repoA" }` in a multi-repo workspace.
- One worktree per repository.

## Lifecycle Modes

### Managed / ephemeral

Shorthand:

```yaml
worktree: true
```

Lifecycle:

1. Promote/resolve the run so `workflowKey` and `runRef` are stable.
2. Acquire the existing lineage runner lock before any worktree mutation.
3. Capture the source checkout path, target branch, and exact base commit.
4. Under the short repository worktree-mutation lock, create an ownership record,
   managed branch, and linked worktree idempotently.
5. Persist provisioning worktree runtime metadata through `WorkingFileManager`.
6. Acquire an exclusive execution lease for that worktree.
7. Seed `.ctrlyoke/.gitignore` into the worktree before any harness write.
8. Run the configured setup command once and persist its outcome.
9. Persist ready worktree runtime metadata through `WorkingFileManager`.
10. Run every workflow phase there.
11. On terminal settlement, stop integrations/sidecars and clean provider artifacts.
12. Auto-commit all tracked/untracked, non-ignored changes after identity and
    runtime-path guards pass.
13. Optionally merge when explicitly requested.
14. Remove the worktree directory unless `keep: true` or safe finalization
    failed.
15. Release the execution lease, then the lineage runner lock, and persist the
    final independent landing/merge/directory outcomes.
16. Leave a non-empty branch and ownership record for review/cleanup.

Terminal settlement includes successful completion, cancellation, stopped
execution, and handled execution failure. Partial work is still data and must be
landed safely. A pause is not terminal: the worktree and lease stay live.

If auto-commit fails because of Git identity, hooks, signing, filesystem errors,
or another cause, finalization becomes blocked and the directory remains.

Before staging or committing, verify that the checkout is still attached to the
recorded managed branch and that the branch/ref identity still matches the
ownership record. An agent may detach HEAD, switch branches, delete/reset the ref,
or leave a Git operation in progress; any mismatch blocks finalization and keeps
the directory. Use a deterministic, non-AI commit message and a bounded,
non-interactive Git invocation.

A managed run whose final HEAD still equals its captured base has no result to
review. When `keep` is false, remove the worktree and delete the still-owned empty
branch under the repository mutation lock, then record `landingOutcome:
"no-changes"`. When `keep` is true, keep both directory and branch even though the
outcome is `no-changes`.

After a no-change run has durably recorded that both branch and directory are
gone, remove its now-resource-free ownership record. If a crash interrupts that
sequence, the record remains as a reconciliation tombstone.

### Named / persistent

Shorthand:

```yaml
worktree: ui-work
```

Behavior:

- Resolve an existing worktree by its local branch name.
- If the branch exists but is not checked out, attach a worktree under the
  configured root.
- If neither branch nor worktree exists, create both from the captured base.
- Reject a named branch already checked out in the initiating source checkout;
  that is ordinary execution, not an isolated target. If it is checked out in a
  different linked worktree, target that discovered path.
- Acquire an exclusive execution lease before running setup or workflow code.
- Run setup only when ctrlyoke creates the named worktree.
- Never auto-commit, merge, remove, or delete the branch.

Once created, a named worktree is user-owned even though ctrlyoke performed the
initial creation.

An existing named worktree may already be dirty. Record and display that fact but
do not block: named mode is explicitly user-owned and does not auto-commit or
remove anything. Its run-start `baseCommit` is the named branch's HEAD, distinct
from the optional labeled comparison base used for ahead/behind display.

Setup is at-most-once automatically, not blindly rerun after a crash. Persist
`pending | running | succeeded | failed`; an interrupted or failed setup blocks
the run and offers an explicit Retry Setup action. Retrying may repeat a
non-idempotent command, so it always requires user action. The setup command uses
the shared script process runner, `executionRoot` as cwd, the normal script
timeout, and workflow/CLI variable substitution. Extract the shell/process runner
from `EndConditionEvaluator`; its current execution method is private, so there is
no reusable setup runner yet.

Worktree-targeted runs do not retain PTYs, session-activity watchers, provider
sidecars, or workspace artifacts after terminal settlement. This applies to named
as well as managed mode: releasing an exclusive lease while a retained process can
still modify that directory would invalidate the lease guarantee. Pause is not
terminal and may retain them.

### Finalization order

Managed finalization must occur in this order:

1. Stop session activity watchers and background monitors.
2. Dispose integrations rooted in the worktree; do not park them for injection.
3. Restore/clean provider-specific hook and MCP config artifacts.
4. Remove temporary runtime trust grants that are no longer needed.
5. Auto-commit the remaining user/agent changes.
6. Persist the landing result and final managed branch tip.
7. Perform optional merge handling while holding a separate exclusive lease on
   the source checkout.
8. Remove the worktree if allowed.
9. Release the execution lease.
10. Persist final landing, merge, branch, and directory outcomes.

The lease remains held through commit and removal so another process cannot
enter halfway through finalization. Because leases live in Git common-directory
storage rather than the checkout or its removable worktree-admin directory,
`git add -A` cannot commit them and successful worktree removal cannot erase the
lease before owner-verified release.

Provider cleanup is best-effort today (`CliIntegration.cleanupWorkflowArtifacts`
swallows some unlink failures). Managed finalization requires a strict cleanup
mode/result: if a generated hook, MCP config, statusline artifact, or restored
workspace config cannot be proven cleaned, block the commit and keep the worktree.
Provider-specific sidecars (e.g. `ClaudeStatuslineSidecar.stop()`) and
`SessionActivityWatcher` instances must be included in this barrier.

### Completion result

Branch state and directory state are independent:

```typescript
interface WorktreeCompletionResult {
  landingOutcome: "landed" | "no-changes" | "blocked";
  mergeOutcome?:
    | "fast-forward"
    | "merge-commit"
    | "conflict"
    | "blocked"
    | "abort-failed";
  directoryOutcome: "removed" | "kept" | "remove-failed";
  branchState: "present" | "deleted" | "missing";
  branchName: string;
  targetBranch?: string;
  conflictFiles?: string[];
  autoCommitted?: boolean;
  message?: string;
}
```

`keep: true` controls directory cleanup. It does not erase landing/merge outcome;
the only branch consequence is that an attached no-change branch cannot be
deleted while its kept worktree remains.

## Optional Merge

Merging is opt-in:

```yaml
worktree:
  mode: managed
  merge: true
```

The merge target is the source checkout and branch captured when the managed
worktree was created. It is never "whatever branch happens to be current later."

Merge sequence:

1. Auto-commit worktree changes.
2. Compare managed `HEAD` to the captured base commit.
3. If unchanged, apply the managed no-change rule: remove the worktree and
   delete the empty owned branch unless `keep: true`.
4. Require the source checkout to still be on the captured target branch.
5. Require the source checkout working tree and index to be clean.
6. Acquire an exclusive execution lease for the source checkout; a managed
   worktree's own lease does not protect the merge target from ordinary workflows.
7. Re-run the branch/cleanliness guards after acquiring that lease.
8. Attempt `git merge --ff-only`.
9. If the histories diverged, attempt a non-interactive `git merge --no-ff --no-edit`.
10. On conflict, collect NUL-delimited unmerged paths **before** `git merge --abort`.
11. Verify abort restored a clean, non-merging state. Report `abort-failed`
    distinctly because the source checkout then needs manual recovery.
12. Release the source-checkout lease and leave the managed branch for manual
    resolution/review.

The source checkout may advance on the same target branch while the agent runs;
that simply determines whether the merge is fast-forward or a merge commit.

Creation itself does not require a clean source checkout because a worktree is
created from a commit, not the source index. Uncommitted source-checkout changes
are not copied into the worktree; surface that fact in run details. Declarative
merge is unavailable when the captured source checkout was detached.

The same merge engine serves:

- Declarative `merge: true`.
- The dashboard's explicit **Merge** action.

The UI action must not be exposed before that engine exists.

Two concurrent merge attempts therefore serialize through the source checkout's
exclusive lease. A lease conflict fails immediately with owner details; merge
does not wait or queue.

## Discovery and Ownership

Run `git worktree list --porcelain -z` through a single parser that represents:

- Worktree path.
- HEAD commit.
- Optional local branch.
- Detached state.
- Bare state.
- Locked state and reason.
- Prunable state and reason.

Parse NUL-delimited records so spaces, newlines, quoting, and non-ASCII paths
cannot corrupt discovery.

Discovery is not ownership. A `ctrlyoke/` branch prefix is a naming convention,
not proof that ctrlyoke may delete anything.

### Durable ownership records

Managed worktrees get an atomic record under the repository's Git common
directory:

```text
<git-common-dir>/ctrlyoke/managed-worktrees/<branch-hash>.json
```

The record includes:

- Schema version.
- Branch name and worktree path.
- Source checkout root.
- Base commit and target branch.
- Last ctrlyoke-verified branch tip (updated after landing/merge).
- Host `stateRoot`.
- `workflowKey` and `runRef`.
- Created timestamp.
- Current directory/branch outcomes.

This survives linked-directory removal and supports safe branch cleanup. A
branch prefix, path under the configured worktree root, or runtime working file
alone is never sufficient authority to delete a branch.

Ownership-record writes and branch/worktree mutations use one short arbitration
lock under the Git common directory and `AtomicFileUtils` for replacement. Before
deleting a branch, verify that its current tip still equals the last tip recorded
by ctrlyoke; a branch name that a user deleted and recreated is no longer owned.

### Recovery

Creation and finalization are idempotent:

- If a managed run resumes and its ownership record plus worktree still exist,
  reuse them.
- If the directory is gone but the branch exists, compare its tip with the
  recorded base/final tip and reconcile as landed, no-changes, or orphaned; do
  not label an unchanged or unexpectedly moved branch as landed.
- If the worktree exists but the originating runner and execution lease are
  stale, expose it as recoverable.
- If the branch was deleted manually, remove the stale ownership record after
  confirmation or safe reconciliation.

Activation performs read-only discovery and reports recoverable managed
worktrees. It does not delete user worktrees automatically.

## Concurrency: Shared and Exclusive Execution Leases

The existing `runner.json` remains the per-lineage execution lock. Worktree
support adds a second mechanism for directory-level coordination across
ctrlyoke instances.

A single exclusive `execution-lock.json` would unnecessarily prevent today's
parallel non-worktree workflows. Use a lease set instead:

| Run                            | Lease mode           | Compatible leases in the same execution root |
| ------------------------------ | -------------------- | -------------------------------------------- |
| Ordinary non-worktree workflow | `shared-native`      | Other `shared-native` leases                 |
| Managed worktree workflow      | `exclusive-worktree` | None                                         |
| Named worktree workflow        | `exclusive-worktree` | None                                         |

Leases are scoped by **canonical lease-scope identity**, defined once as: the
worktree-specific absolute Git directory (`git rev-parse --absolute-git-dir`)
when the execution root is inside a Git worktree, and the canonical execution-root
path otherwise. Every storage path and comparison derives from that identity.

Therefore:

- Several ordinary workflows can continue running in the source checkout.
- Managed worktrees run concurrently with them because each has a unique root.
- Different named worktrees run concurrently.
- Two worktree-targeted workflows cannot use the same named worktree.
- A worktree-targeted workflow cannot enter a named worktree while a VS Code
  window opened on that worktree is running ordinary workflows there.
- Ordinary workflows started in a directory with an exclusive worktree lease
  are blocked until that lease ends.

Parallel native workflows retain today's interference risk by explicit design.
Users choose worktree mode when they require isolation.

Global acquisition order is: lineage runner lock → short repository-mutation
lock (release it immediately after the mutation) → target execution lease →
optional source-checkout merge lease. Never wait for an execution lease while
holding the repository-mutation lock. Release persistent locks in reverse order.
Ordinary native runs acquire their shared execution lease before any workflow
script or harness side effect.

### Lease storage

For Git roots, store leases centrally under the canonical Git common directory,
partitioned by a hash of the canonical scope identity:

```text
<git-common-dir>/ctrlyoke/execution-leases/<scope-hash>/
  scope.json
  arbitration.lock
  leases/<owner-token>.json
```

`scope.json` records the unhashed canonical identity so a hash/path mismatch fails
closed. Do not put the lease directory beneath the worktree-specific Git admin
directory: `git worktree remove` deletes that directory, which would erase the
lease before finalization can perform an owner-verified release.

For a non-Git ordinary execution root, fall back to:

```text
<executionRoot>/.ctrlyoke/execution-leases/
```

Each lease contains:

```typescript
interface ExecutionLease {
  ownerToken: string;
  mode: "shared-native" | "exclusive-worktree";
  pid: number;
  runner: "vscode" | "cli";
  instanceId: string;
  stateRoot: string;
  executionRoot: string;
  workflowKey: string;
  runRef: string;
  startedAt: number;
  lastHeartbeat: number;
}
```

Acquisition performs scan, stale cleanup, compatibility validation, and
exclusive file creation while holding the scope's short arbitration lock. This
prevents a shared/exclusive check-create race across processes. Every run owns
its own lease file, so one shared workflow finishing cannot release another's
lease.

Reuse the existing runner-lock safety primitives rather than inventing a second
staleness model:

- Random owner token.
- `STALE_HEARTBEAT_MS = 30_000` — a lease is reclaimable when its PID is dead or
  its `lastHeartbeat` is older than this.
- `HEARTBEAT_INTERVAL_MS = 5_000` — currently a literal in
  `WorkflowInstance`; extract it alongside the staleness threshold.
- Owner-token verification on update and release.
- Actionable owner information in conflicts.

Do **not** reuse `WorkflowLockManager`'s five-second live-owner acquisition wait.
Execution-lease conflicts are specified to fail immediately after the short
arbitration critical section; waiting would contradict the no-queue UX. Extract
the token/heartbeat/staleness helpers, not one lock manager's complete acquire
algorithm.

The exclusive lease for a paused worktree run remains owned and heartbeating for
the lifetime of the loaded `WorkflowInstance`, even though the per-lineage runner
lock is released between execution cycles. On process shutdown it becomes stale
and recoverable. Resuming from another live process conflicts rather than stealing
the reservation. Terminal settlement releases it; `keep: true` does not keep a
lease after settlement.

### Lease UX

An incompatible live lease is a hard failure in the first release. Do not queue
or prompt.

The error reports:

- Owning workflow and run.
- Runner/instance and PID.
- Owning state root.
- Lease age.
- Retry action.
- Open Owning Workspace action where available.

Worktree discovery renders any root with a live lease as **in use**.

## Workflow Schema

`worktree` is workflow-level only. Introduce a separate
`workflowOnlyProperties` definition and apply it to both top-level workflow
shapes (single-step root and multi-step/working-file root). Do not add it to the
shared `executionProperties` definition used by nested steps and runtime
metadata.

The schema must also split the top-level single-step wrapper from the nested
`workflowStep` definition. Today `promptStep` is permissive while `scriptStep`
uses `additionalProperties: false`; merely omitting `worktree` from
`executionProperties` would still allow it silently on nested prompt steps, and
adding a negative guard to the shared step definition would reject it at the
single-step root too. Add root-only wrappers (or equivalent semantic validation)
so `worktree` validates at the root and is explicitly rejected on every nested
`steps[]`, `finalStep`, and prompt `_runtime` object.

Supported forms:

```yaml
worktree: false                 # explicit no-worktree (overrides the settings default)
worktree: true                  # managed shorthand
worktree: ui-work               # named shorthand
# omitting `worktree` entirely inherits `defaults.worktree` from settings

worktree:
  mode: managed
  merge: false
  keep: false
  base: main
  setup: npm ci

worktree:
  mode: named
  branch: ui-work
  base: main
  setup: npm ci
```

TypeScript contract:

```typescript
type WorktreeConfig =
  | boolean
  | string
  | {
      mode: "managed";
      merge?: boolean;
      keep?: boolean;
      base?: string;
      setup?: string;
    }
  | {
      mode: "named";
      branch: string;
      base?: string;
      setup?: string;
    };
```

Rules:

- `true` means `{ mode: "managed" }`.
- A string means `{ mode: "named", branch: value }`.
- `false` means ordinary execution, explicitly, and overrides any configured
  default.
- **Omission means "inherit `defaults.worktree` from settings."** It is not a
  synonym for `false`. `PromptFileParser` must therefore not normalize an absent
  `worktree` to `false` at parse time; absence has to survive into resolution so
  the settings tier can supply a value. See _Settings Defaults_ below.
- `merge` and `keep` are not legal in named mode.
- `branch` is required in named object mode and illegal in managed mode.
- The default base is the source checkout's exact `HEAD` commit.
- `base` must resolve to a commit before any directory is created.
- `base` affects creation only; it is ignored when resolving an existing named
  branch/worktree.
- `setup` runs once only when ctrlyoke creates the worktree.
- An empty named shorthand/branch is invalid.
- Managed branch names use a bounded workflow slug plus `runRef`; physical
  directory names use a separately bounded slug plus a hash of the stable
  workflow/run (or named-branch) identity. Branch strings are never path input.

JSON Schema performs structural and coarse character validation. Runtime
validation calls:

```text
git check-ref-format --branch <branch>
```

The validated branch string is never used as a filesystem-relative path.
There are no reserved string names; a quoted branch named `auto` is simply a
named branch.

Expose schema forms only when their behavior is implemented. For example,
`merge` must not validate before the merge engine exists.

`schemas/workflow-schema.json` is the source; regenerate
`schemas/workflow-schema.yaml` with `npm run generate-schema`. Update schema tests
for both root shapes and every forbidden nested location.

Dry-run/preview must never create a branch, worktree, ownership record, or lease.
It performs read-only semantic validation and reports the configured mode, base,
eligibility result, and planned root (an exact managed branch/path is unavailable
until a real `RunRef` is allocated).

## Settings Defaults and Resolution

Worktree has a global default tier. An earlier revision of this plan forbade one
("worktree behavior must be explicit in the workflow") but never gave a reason,
and the prohibition is wrong for the common case: a user who wants a managed
worktree for every run should not re-select it on every new workflow. That is
what defaults are for.

The default tier is real but narrow. Worktree resolves across exactly two tiers:

```text
workflow-authored value  →  settings default  →  no worktree
```

There is **no prompt/step tier**. Step-level worktree overrides stay forbidden by
the schema, so worktree does not use `PropertyResolver.resolve()`'s
prompt > workflow > settings chain. Resolution is a dedicated two-tier helper.

### Settings shape

Two distinct settings groups, because they answer different questions:

`defaults.worktree` — a workflow default, mirrors the rest of `defaults.*`,
writable at user and workspace scope:

```jsonc
"defaults": {
  "worktree": {
    "mode": "none" | "managed" | "named",  // default "none"
    "branch": "ui-work",                   // named mode only
    "base": "main",
    "setup": "npm ci",
    "keep": false,
    "merge": false
  }
}
```

`worktrees` — machine/repository configuration, **user scope only**, unchanged
from the earlier revision in intent:

```jsonc
"worktrees": {
  "root": "~/.ctrlyoke/worktrees"   // absolute or ~-prefixed
}
```

`worktrees.root` stays user-scope-only for the reason already established under
_Placement guards_: workspace-scope configuration must not be able to redirect
checkout creation to an arbitrary external directory. Schema validation alone
cannot express that; the settings write path must reject a workspace-scope write
to `worktrees.root`, and the settings UI must render the row scope-locked with an
explanation rather than silently discarding the value.

`defaults.worktree.mode` uses the string `"none"` rather than `false`, because a
settings enum with a `SettingSource` badge and a reset affordance reads better as
a three-value dropdown than as a tri-state boolean. Resolution maps `"none"` to
"no worktree."

### Resolving an inherited mode is not the same as an authored one

This is the guard rail that makes a global default safe to carry between
workspaces, and it must be implemented, not assumed.

Worktree preflight **hard-fails** on an ineligible workspace — no Git repository,
more than one repository, or a named root outside the sole repository (see
_Workspace Eligibility_). A user-scope `mode: managed` follows the user into every
workspace they open, including ineligible ones, where it would fail every single
workflow at preflight until the user found and cleared the setting.

Therefore preflight distinguishes the value's origin:

| Origin of the resolved mode           | Ineligible workspace behavior                              |
| ------------------------------------- | ---------------------------------------------------------- |
| Authored in the workflow definition   | Hard failure with the eligibility reason (unchanged)       |
| Inherited from `defaults.worktree`    | Degrade to ordinary execution, record and surface a notice |

The degrade is recorded on the run — not merely logged — so the status readout
can state that the configured default did not apply and why. An explicit authored
value never degrades: the user asked for isolation by name and silently not
providing it would be worse than failing.

`ExecutionWorkspace` construction therefore needs the resolved worktree config
plus its origin (`"authored" | "default"`), not just the config.

### Named mode as a default is sharp, and the UI must say so

`mode: managed` is safe to default on: every run gets its own directory and
branch, so N concurrent workflows coexist. `mode: named` is not equivalent — every
workflow in the workspace targets one directory, and worktree runs take an
`exclusive-worktree` lease, so the second concurrent workflow fails immediately on
lease conflict. A workspace-wide named default effectively serializes all
execution in that workspace.

Named is still permitted as a default, but both the settings row and the drawer
must carry an explicit warning when the resolved mode is named — in the drawer
only when the value was inherited, since an authored named workflow is a
deliberate choice the user is already looking at.

### `merge` and `keep` defaults

`merge: true` is the only worktree option that writes to the user's live checkout.
It is settable as a default for consistency, and it fails safe already: the merge
engine requires the source checkout to still be on the captured target branch and
to be clean, takes an exclusive lease on it, and aborts cleanly on conflict. The
settings row must nevertheless state plainly that it merges into the working
checkout after every run. As with the schema form, the `merge` default must not be
exposed before the merge engine exists.

`keep` interacts with undo and deserves its own note in the UI. Settled Decision
\#9 means a managed run whose directory is removed has no filesystem undo, because
content restore is ctrlyoke's only undo mechanism. With a managed default on, that
is now true of every run rather than only opted-in ones. The drawer must say so at
the point of choosing — a description on the Keep control — not only after the run
lands.

### Threading

- `schemas/settings-schema.json` gains `defaults.worktree` and top-level
  `worktrees`, both `additionalProperties: false`.
- `CtrlYokeSettings.ts` and `CtrlYokeConfigService` carry both groups; the
  config service enforces the user-only scope rule for `worktrees.root`.
- `FullGlobalSettings` / `WebviewMessageTypes` expose them with the usual
  `sources` entries so `SettingInputRow` can render scope badges and resets for
  `defaults.worktree.*` and `worktrees.root`.
- The webview `GlobalSettings` store type gains `worktree`, and the settings
  store gains `getEffectiveWorktree()` alongside the existing
  `getEffectiveExecutionMode()` family.

### `ExecutionRootLeaseManager`

`src/core/orchestration/ExecutionRootLeaseManager.ts` owns the shared/exclusive
lease protocol and reuses/extracts the heartbeat and owner-token primitives
currently embodied by `WorkflowLockManager`.

It is separate from lineage runner locking because the two locks answer
different questions:

- Runner lock: who executes this lineage/run?
- Execution lease: which runs may use this directory concurrently?

### Runtime trusted roots

Do not persist worktree paths into `ExternalRootsTrustStore`; that store records
user decisions about workspace-requested external roots.

Add a process-session, owner-token/ref-counted runtime trusted-root registry.
File-access callers combine:

- Workspace roots.
- User-approved external roots.
- Validated runtime worktree roots.

The harness itself receives the worktree through its remapped execution
workspace, not by pretending it is a user-approved external root.

Grant lifetime:

- Managed ephemeral: while the worktree exists.
- Named/kept: while the associated run/session is loaded or discoverable in the
  current ctrlyoke process and the path still resolves to the same repository.

This keeps output file links usable after a named run completes without
persisting a permanent trust decision.

This registry is for backend file access/UI links only. It must not feed harness
`--add-dir` assembly. Harness roots come from `ExecutionWorkspace`, while approved
external roots retain their existing state-workspace trust identity.

### Repo discovery and snapshots

Snapshot capture receives the execution workspace's remapped named roots.
Hosted SCM/file attribution may additionally probe active runtime worktree
roots, but must distinguish the source checkout and linked checkout rather than
assuming they are one toplevel.

Adding only the worktree path as an extra global repo probe is insufficient:
prefix mapping and snapshot capture must also use the execution-scoped roots.

## Snapshots, Diffs, and Undo

### Capture

Before/after snapshots run against:

- `executionRoot` for the primary capture.
- Remapped `namedWorkspaceRoots` for multi-root segments.
- The linked worktree's Git toplevel, not the source checkout.

Persisted snapshot repo metadata therefore names the actual checkout used by the
agent.

### Active and persistent worktrees

Named and `keep: true` worktrees support existing per-step filesystem undo as
long as:

- The worktree still exists.
- It resolves to the recorded repository/branch identity.
- The undo coordinator uses the recorded execution root and remapped named
  roots, not the window's current source roots.

### Landed managed branches

**There is only one undo mechanism, and it is filesystem content restore.**
`UndoRedoCoordinator` routes every undo and redo through
`snapshotService.undoFiles(...)` in `src/ui/UndoRedoCoordinator.ts`, which writes
stored before-content back to resolved paths. No revert, reset, or checkout path
exists. Git participates only as a _source of before-content_ when a snapshot's
base source is `GIT_HEAD` — never as the mechanism that performs the undo.

So after a managed directory is removed there is no "git-based undo" to fall back
on. What survives is the recorded diff and its attribution, which are persisted
snapshot data and remain fully viewable. Reverting a landed branch is an ordinary
Git operation the user performs themselves.

After a managed directory is removed:

- Keep snapshot diffs and repo attribution viewable.
- Disable filesystem undo with a clear "worktree landed as branch" explanation.
- Offer View Branch Diff and, when implemented, Merge.

**Disabling the button is not sufficient.** `applySnapshotEntries` resolves paths
against `getVsCodeNamedWorkspaceRoots()` in `src/ui/UndoRedoCoordinator.ts` —
the _current window's_ roots, not the roots the run actually executed against. Any
undo entry belonging to a worktree run would therefore resolve into the source
checkout and write there. The coordinator itself needs a guard that refuses to
apply an entry whose recorded execution workspace is absent or does not match, so
a stale UI state, a queued request, or a future caller cannot bypass the UI check.

The current undo messages also carry a client-supplied `workspacePath`. Remove
that authority from the protocol: send the addressed `workflowKey`/`runRef` plus
the target, load the run's persisted worktree metadata on the backend, and derive
`executionRoot`/`namedWorkspaceRoots` there. For ordinary runs the backend derives
the existing workspace roots. For named/kept worktrees it canonicalizes the path,
verifies repository common-dir, branch, and recorded checkout identity, and only
then calls `undoFiles`. A missing/removed/mismatched checkout is a hard refusal.
The same rule applies to redo and workflow-wide undo, not only prompt undo.

Recreating a temporary worktree to apply a reverse patch and commit the result is
deferred. The UI must not silently redirect historical undo into the user's source
checkout.

## Dashboard and CLI UX

### Workflow Properties drawer — authoring controls

Worktree is a **workflow-level** property, so it belongs in
`WorkflowPropertiesPanel.tsx` and must **not** appear in the per-prompt
`PropertiesDrawer`. The schema forbids `worktree` on `steps[]`, `finalStep`, and
prompt `_runtime`; the prompt drawer omitting it is the UI half of that same rule.

Placement is the **Harness page** (`DRAWER_PAGES.HARNESS`), directly after the
Additional Args / Execution Mode row. That page is already the "how and where this
runs" page, and worktree is the sibling of Execution Mode: one decides process
shape, the other decides working directory.

Layout, using the existing `DrawerRow` / `FormField` / `AnimatedSection`
primitives already used on that page:

```text
┌─────────────────┬─────────────────┐
│ Additional Args │ Execution Mode  │   (existing row 3)
├─────────────────┼─────────────────┤
│ Worktree [None▾]│ —               │   mode = none: single control, no growth
└─────────────────┴─────────────────┘

  ▼ mode = Managed
┌─────────────────┬─────────────────┐
│ Worktree [Mngd▾]│ Base   [main   ]│
├─────────────────┴─────────────────┤
│ Setup  [npm ci                   ]│
│ ☐ Keep directory   ☐ Merge on done│
└───────────────────────────────────┘

  ▼ mode = Named
┌─────────────────┬─────────────────┐
│ Worktree [Nmd ▾]│ Branch [ui-work]│
├─────────────────┼─────────────────┤
│ Base    [main  ]│ Setup  [npm ci ]│
└─────────────────┴─────────────────┘
```

Rules:

- The mode dropdown is `CustomSelect` with **None / Managed / Named**, sourced
  from a `WORKTREE_MODE_OPTIONS` constant in `DashboardConstants.ts` beside
  `EXECUTION_MODE_OPTIONS`. The literal mode strings are flow-control values and
  must be constants, not inline strings.
- Every dependent control lives inside an `AnimatedSection` keyed off the resolved
  mode, matching how the Validation page reveals pre/end-condition fields. When
  mode is None the page costs one extra row and nothing else.
- `branch` is required in named mode. Empty branch is a validation error surfaced
  through the existing `FieldDiagnostic` / `fieldValidationBorderClass` path, not
  a silent save. Coarse `git check-ref-format` character rules can be checked in
  the webview for immediate feedback; the authoritative check stays server-side.
- `keep` and `merge` render only in managed mode, because the schema makes them
  illegal in named mode.
- `merge` must not be rendered before the merge engine exists (Phase 4), matching
  the schema-exposure rule.
- The Keep control's description states that removing the directory ends
  filesystem undo for that run.
- When the resolved mode came from settings rather than the workflow, show the
  inherited-value treatment the page already uses — the control reads the
  effective value and `SetAsDefaultButton` stays hidden until it diverges.
- A named mode inherited from settings shows the concurrency warning described
  under _Settings Defaults_.
- The whole block inherits the existing CLI-managed read-only treatment; the
  panel body already disables pointer events when `managedBy === RUNNER_IDS.CLI`,
  so no extra handling is needed.

Wiring follows the established handler shape exactly — an optimistic
`updateWorkflowProperty("worktree", value)`, `syncWorkflowPropertiesForUndo()`,
then `postWorkflowDefinitionMutation(vscode, { type: UPDATE_WORKFLOW_PROPERTY, … })`.
Changing the mode dropdown is a multi-field edit (mode plus the sub-options it
seeds or clears) and must go through `postWorkflowPropertiesUpdate()` so it lands
as one undo entry, the same way `handleHarnessChange` batches model and
additional-args.

Three existing behaviors need explicit worktree cases, and all three are easy to
miss:

- `isDifferentFromGlobal()` needs a deep-comparison branch for `worktree`,
  normalizing `false` / `"none"` / absent to one canonical form, in the same
  manner as the existing `mcpServers` and `toolPermissions` branches. Without it
  the Set as Default button appears on unchanged workflows.
- `handleResetAllToDefault()` must include `worktree` in its updates object, and
  reset any local mode state it keeps, alongside the existing session-id and
  condition resets.
- Selecting a mode seeds the sub-option fields from `defaults.worktree` — picking
  Managed should present the configured base/setup/keep, not blanks — mirroring
  how `handleHarnessChange` seeds model and additional args from the harness
  defaults.

### No tab badge for worktree

Worktree must **not** badge the Harness tab, and `useDrawerTabOverrides` must not
gain a `harness` entry for it.

Navigation tabs have two independent channels, and worktree belongs to neither:

- **The primary icon — its glyph and its color — carries state.**
  `permissionModeIconOverride` swaps both for `dangerouslyAllowAll` (a
  `workspace-untrusted` glyph in `text-error-fg`); the other four helpers
  (`getHooksTabOverride`, `getMcpTabOverride`, `getValidationTabOverride`,
  `getContextTabOverride`) recolor only.
- **The overlay badge carries diagnostics — errors and warnings only.** The one
  badge in `useDrawerTabOverrides` comes from `getPermissionTabOverride`'s
  `hasCompatibilityWarning`.

"Worktree is enabled" is state, so it has no claim on the badge slot. This
convention is recorded in `HARNESS_COMPATIBILITY_PORTABILITY_PLAN.md` under _Tab
warning badges_; this plan follows it rather than restating it.

The Harness tab has no state channel at all, which is the deeper reason worktree
cannot indicate there. Its primary icon is a brand logo, and neither half of the
state channel is usable: swapping the glyph would destroy the identity the tab
exists to show, and `HarnessIcon` renders an `<img>` with a base64 data URI, so
`TabIconOverride.color` is a silent no-op against it. That leaves only the badge
slot, which is reserved for diagnostics.

Two consequences:

- **Do not add badge rendering to the `HarnessIcon` branch of
  `SegmentedTabBar.tsx`.** The badge overlay currently exists only in the
  `codicon` branch. With no state badge and no modeled harness-level diagnostic,
  that slot would have zero consumers, and the compatibility plan explicitly
  forbids building badge plumbing before a domain is enabled to feed it. If
  harness availability later becomes a modeled error, the slot gets added then, by
  that plan.
- **The Harness tab must never receive `codicon`, `color`, `activeColor`, or
  `hoverColor` overrides.** `SegmentedTabBar` resolves
  `override?.codicon ?? tab.codicon`, so supplying `codicon` for the Harness tab
  would take the codicon branch and replace the brand logo with a generic glyph.
  Only `badgeCodicon`/`badgeColor` are ever legitimate there.

Worktree state is surfaced in the status components below instead, which is where
it belongs and where it is more legible than a 13px overlay.

### Settings UI

Two placements, matching the two settings groups:

**`defaults.worktree` → `DefaultsHarnessPage.tsx`,** as a third bordered block
after Execution Defaults, using `SettingInputRow` with `path` values
(`defaults.worktree.mode`, `.branch`, `.base`, `.setup`, `.keep`, `.merge`) so
each row gets its scope badge and reset button. This keeps the existing 1:1
mirror between `defaults.*` settings pages and drawer pages: worktree sits on the
Harness page in both, so a user finds the default where they found the control.
Sub-option rows follow the same progressive disclosure as the drawer.

**`worktrees.root` → a new top-level Worktrees section.** It is machine
configuration, not a workflow default, so it does not belong in the
`defaults.*` mirror. Add `{ id: "worktrees", label: "Worktrees", icon:
"codicon-source-control" }` to `ALL_TABS` in `GlobalSettingsDrawer.tsx` and a
`WorktreesSection.tsx` beside `ExecutionSection.tsx`. It holds:

- `worktrees.root`, rendered scope-locked to user scope with an explanation when
  the workspace scope is active, per the placement guard.
- The resolved effective root, shown read-only, since resolution has three tiers
  and a user needs to see which one won.
- Later, the Manage Worktrees list — ownership, lease state, branch state, age,
  and the safe remove/prune/branch-cleanup actions. That is Phase 4 and this
  section is where it lands, which is the other reason it is its own section
  rather than a row on a defaults page.

### Run status and actions

Status information belongs in the status surfaces, not in navigation chrome. Two
components own it:

**`components/workflow/WorkflowStatus.tsx`** — the split button's "what is this
workflow doing right now" row. It already carries exactly this class of

Running:

```text
▶ ui-refactor   [claude-cli] [sonnet]  ● running
  Branch: ctrlyoke/ui-refactor/run-2026-07-27T14-02-11-123Z
```

Completion:

- `✓ branch ready — 12 files` with **View Diff**
- **Merge** only after the shared merge engine exists
- `✓ merged (fast-forward)`
- `✓ merged (merge commit)`
- `✓ no changes`
- `⚠ merge conflict — branch preserved`
- `⚠ merge blocked — source branch changed or checkout is dirty`
- `⚠ commit blocked — worktree kept at …`
- `⚠ worktree removal failed — branch safe, directory kept`

Actions:

- **View Diff** uses the recorded base commit and managed branch.
- **Open Worktree in New Window** appears only while the directory exists.
- **Merge** re-runs every dirty/branch/lease guard at click time.
- **Manage Worktrees** lists ownership, lease state, branch state, age, and

## Cleanup and Retention Decisions

### Concurrency warning — deferred, not blocking

There is no hard maximum in the first release. Repository size, dependency layout,
and available disk vary too much for a universal cap. That much is settled.

**The warning threshold is not settled and must not be implemented on a guess.**
An earlier draft specified "warn at approximately the sixth active managed
worktree." That number has no basis — it was invented, not measured. Ship without
a threshold, observe real usage, then choose one.

When a threshold is eventually added, it should count live managed execution
leases (not persistent or landed worktrees) and surface the active count plus the
resolved worktree root. Do not add `worktree.maxConcurrent` until usage
demonstrates a need.

### Landed branch retention

Never delete landed branches automatically in the first release.

Manage Worktrees provides bulk cleanup. It may preselect only branches that:

- Have a valid ctrlyoke ownership record.
- Are not checked out in any worktree.
- Have no live/recoverable run or lease.
- Are proven fully merged into their recorded target branch.

Squash/rebase merges are not provable through ancestry and remain explicit
user-selected deletions.

### Manual directory deletion and pruning

Use discovery at activation and mutation on demand:

- Activation performs `git worktree list --porcelain -z` and read-only stale/
  prunable reporting.
- Manage Worktrees offers explicit prune.
- Resolving a requested branch with a stale admin entry offers targeted repair.
- ctrlyoke may automatically reconcile only an entry proven managed by its
  ownership record and protected by no live lease.

Never automatically run `git worktree prune --expire now` against user-owned
entries. A temporarily unavailable network/removable path can look deleted.

### Execution lease conflicts

Incompatible leases fail immediately with owner details and Retry/Open actions.
No cross-process queue is introduced in the first release.

## Test Matrix

### Root split

- No-worktree paths and arguments remain identical.
- Saved `.code-workspace` state root outside the repo maps safely.
- Several named roots inside one repo remap correctly.
- Non-repo named root and multi-repo workspace refuse worktree mode.
- Script path resolution accepts the worktree and rejects escapes.
- Condition scripts resolve from the execution root; workspace-local agents and
  skills resolve from the execution checkout.
- Authored definition paths inside the repository map lexically for `./` refs;
  outside-repository relative refs fail closed.
- MCP state variables remain rooted at `stateRoot`.
- Approved external roots retain the state workspace's trust identity, while
  overlap with the source checkout is rejected.
- Dry-run performs no Git, ownership, lease, or directory mutation.

### Schema and persistence

- Worktree is accepted at workflow root and rejected on steps/finalStep runtime.
- Parser and loader preserve every shorthand/object form.
- Promotion/re-run keeps the definition and starts fresh runtime metadata.
- Ordinary runtime writes preserve `_runtime.worktree`.
- An absent `worktree` survives parsing as absent and is never normalized to
  `false`, so the settings default can apply.

### Settings defaults

- Omission inherits `defaults.worktree`; `worktree: false` overrides a configured
  default and runs ordinarily.
- An authored worktree value in an ineligible workspace hard-fails.
- An inherited worktree value in an ineligible workspace degrades to ordinary
  execution and records the notice on the run.
- A workspace-scope write to `worktrees.root` is rejected rather than silently
  applied or discarded.
- Sub-option defaults (`base`, `setup`, `keep`, `merge`) apply to both managed and
  named workflows; `keep`/`merge` remain illegal on an authored named workflow.
- The `merge` default is not exposed before the merge engine exists.

### Leases

- Two shared-native leases coexist.
- Exclusive acquisition fails while any live lease exists.
- Shared acquisition fails while an exclusive lease exists.
- Exclusive leases on different roots coexist.
- Stale shared/exclusive leases are reclaimed.
- Owner-token release cannot delete another run's lease.
- Scan/check/create is race-safe across processes.
- Successful worktree removal cannot erase a centrally stored lease before
  owner-verified release.
- A paused worktree run keeps heartbeating its exclusive lease; shutdown makes
  it stale/recoverable.
- Managed merge acquires an exclusive lease on the source checkout and conflicts
  with live native shared leases.

### Named worktrees

- Discover existing branch checkout.
- Reject the named branch when its checkout is the initiating source checkout.
- Attach an existing un-checked-out branch.
- Create a missing branch/worktree and run setup once.
- Failed/interrupted setup never auto-retries; explicit retry updates the
  persisted setup outcome.
- Never commit/remove a named worktree.
- Existing dirty named worktree is reported but remains usable.
- Native run in the same worktree blocks exclusive targeting.
- Terminal named runs dispose retained integrations before releasing the lease.

### Managed worktrees

- Safe branch/path creation from captured base.
- Ownership record creation and recovery.
- Setup success/failure behavior.
- Auto-commit and branch landing.
- Detached/switched/reset managed branch blocks finalization and keeps the
  directory.
- Strict provider-artifact cleanup failure blocks commit.
- Cancellation/failure lands partial work.
- Commit failure keeps the directory.
- Removal failure is reported without losing the branch.
- Retained integrations are disposed before finalization.
- Nothing-to-commit and `keep: true`.
- No-change cleanup deletes only the still-owned empty branch when `keep` is
  false; `keep: true` preserves it because the worktree remains attached.

### Merge

- Target branch changed.
- Dirty source checkout.
- Fast-forward.
- Merge commit.
- Conflict paths captured before abort.
- Abort failure.
- Empty branch cleanup.
- Source execution-lease conflict.

### Snapshots and undo

- Snapshots capture only the worktree checkout.
- Same-repo multi-root segments use remapped paths.
- Named/kept undo targets the worktree.
- Landed managed runs disable filesystem undo and retain diff display.
- The coordinator refuses an undo entry whose recorded execution workspace is
  missing or mismatched, even when invoked directly rather than through the UI.
- An undo entry from a worktree run never resolves paths into the source checkout.
- Undo/redo ignores client-supplied path authority and resolves the addressed
  run's roots on the backend.

### Worktree hygiene

- A monorepo opened as several workspace roots is accepted, not refused.
- A newly created worktree has `.ctrlyoke/.gitignore` before the first harness
  write.
- Auto-commit of a managed run stages no `.ctrlyoke/` runtime path, in a
  repository whose root `.gitignore` says nothing about `.ctrlyoke/`.
- Auto-commit fails as `blocked` rather than committing runtime files when the
  guard trips.
- Condition scripts plus workspace agents/skills resolve from the worktree;
  state-side workflow/template discovery does not grant harness access to the
  source checkout.

### Authoring UI

- The worktree block renders on the Harness page and is absent from the
  per-prompt `PropertiesDrawer`.
- Mode None renders one control and no dependent fields.
- Managed reveals base/setup/keep/merge; named reveals branch/base/setup and
  never keep/merge.
- Selecting a mode seeds sub-options from `defaults.worktree`.
- A mode change lands as a single undo entry, not one per seeded field.
- `isDifferentFromGlobal("worktree")` treats absent, `false`, and `"none"` as
  equivalent, so Set as Default stays hidden on an unchanged workflow.
- Reset-all restores `worktree` from settings along with the other properties.
- An empty named branch is a surfaced field diagnostic, not a silent save.
- No drawer tab gains a worktree badge or icon override; `useDrawerTabOverrides`
  returns no `harness` entry.
- `WorkflowStatus` shows a worktree indicator whose title names the mode and
  branch, on the same `!isNarrow` gate as the terminal indicator.
- `RunSummaryBanner` renders the branch and landing outcome from the run's own
  persisted worktree projection, so a historical run shows its recorded state
  rather than the currently bound instance's.
- Open Worktree renders only while `directoryState` is `present`.
- CLI-managed workflows render the block read-only.

### Security

- Branch traversal strings fail semantic validation.
- Directory name never derives directly from the branch.
- Configured worktree root inside a checkout is rejected.
- Ownership prefix alone cannot authorize deletion.
- Workspace-scope config cannot redirect worktree root placement.

## Settled Design Decisions

1. **No hard concurrency ceiling.** Do not block and do not add a setting. The
   warning threshold itself is explicitly unresolved — ship without one rather
   than guess a number.
2. **No automatic landed-branch retention policy.** Provide explicit bulk
   cleanup and preselect only provably safe merged branches.
3. **Show named-branch ahead/behind counts.** Compare against a labeled,
   recorded base/upstream; never auto-sync.
4. **Discover stale worktrees on activation, prune on demand.** Automatically
   reconcile only entries proven ctrlyoke-owned and inactive.
5. **Lease conflicts are hard failures with owner details.** No queue in the
   first release.
6. **Parallel native workflows remain allowed.** They use compatible shared
   leases; worktree-targeted runs use exclusive leases.
7. **Managed worktree results land as branches by default.** Merge is explicit.
8. **Transient worktree trust is session-scoped, not persisted as a user trust
   decision.**
9. **Managed directory removal disables undo for that run.** ctrlyoke has exactly
   one undo mechanism — filesystem content restore — so there is no git-based
   fallback to degrade to. Diff and attribution display remain; temporary
   recreation is deferred. The coordinator, not just the UI, must enforce this.
10. **Worktree has a settings default tier, guarded by origin.** `defaults.worktree`
    may set mode (including `named`) and every sub-option. Omitting `worktree`
    from a workflow inherits it; `worktree: false` explicitly opts out. An
    ineligible workspace hard-fails an _authored_ worktree value and silently
    degrades an _inherited_ one to ordinary execution with a recorded notice, so a
    user-scope default can travel between workspaces safely. `worktrees.root`
    remains user-scope only.
11. **Workflow/template discovery remains state-side; scripts and
    workspace-scoped agents/skills resolve from the execution checkout.** This
    prevents skill paths and harness directory grants from exposing the source
    checkout. User/bundled assets are unchanged.
12. **A monorepo spanning several workspace roots is supported.** Eligibility
    refuses _multiple repositories_ and roots outside the sole repository — not
    multi-root workspaces as such.
13. **Execution leases are centrally stored by worktree-specific scope.** The
    common directory survives linked-checkout removal; the scope hash keeps
    different worktrees isolated.
14. **Paused worktree runs retain their exclusive lease; terminal worktree runs
    retain no integration or sidecar.** This makes pause/resume and lease ownership
    agree.
15. **Managed no-change runs delete their empty owned branch only when the
    directory is also removed.** `keep: true` preserves the attached branch.
16. **Worktree never badges a navigation tab.** Tab badges are reserved for
    errors and warnings; the primary icon's glyph and color carry state. Worktree
    is state, and it surfaces in `WorkflowStatus` and `RunSummaryBanner`, which
    are the status surfaces. The Harness tab in particular has no usable state
    channel — its brand `<img>` ignores color overrides and its glyph is its
    identity — so no `SegmentedTabBar` badge slot is added for it.

## Reversed Decisions and Why

### Default auto-merge → land the branch

Automatically rewriting the source checkout creates unnecessary risk and fights
the review workflow. A shared branch already gives single-window users a
reviewable result.

### Nested `.ctrlyoke/worktrees/` → sibling directory

Nested worktrees break this repository's TypeScript build, attribution,
snapshot walking, and isolation assumptions.

### Single cwd override → typed execution workspace

The current root drives more than spawn cwd: prompt refs, temp files, hooks,
MCP state, session-log discovery, scripts, and snapshots. A typed contract makes
the state/execution split explicit and carries remapped multi-root data.

### One exclusive execution lock → shared/exclusive lease set

A single lock would remove existing parallel non-worktree execution. Shared
native leases preserve that behavior, while exclusive worktree leases protect
the particular directory that must be isolated.

### Non-repo roots pass through → strict first-release eligibility

Passing a live non-repo root to a worktree run is silent partial isolation.
Explicit read-only passthrough can be designed later; the first release refuses
the ambiguous shape.

### State-side workspace assets → execution-side workspace assets

Keeping workspace agents and skills on `stateRoot` appeared to preserve useful
uncommitted definitions, but selected skills expose a filesystem path that the
harness must read. Making that path work would require granting the harness access
to the live source checkout, defeating isolation. Workspace-scoped agents and
skills therefore follow the execution checkout; workflow/template discovery and
user/bundled assets remain state/user-side.

### "Filesystem undo plus git undo" → one undo mechanism

An earlier revision implied a git-based undo tier survived managed directory
removal. It does not exist. `UndoRedoCoordinator` performs every undo through
`snapshotService.undoFiles(...)`; Git only supplies before-content for snapshots
based on `GIT_HEAD`. Removing a managed directory therefore ends undo for that run
outright, leaving diff and attribution display. Reverting a landed branch is an
ordinary user Git operation, not a ctrlyoke feature.

### No global default-on setting → `defaults.worktree` with an origin guard

An earlier revision forbade any global worktree default, asserting that "worktree
behavior must be explicit in the workflow" without ever stating why. No rationale
appeared anywhere in the plan, and the rule fails the ordinary case: a user who
wants a managed worktree for every run should not re-select it on each new
workflow, and "always None" is itself a default — just an unhelpful one.

The real risks were never the existence of a default; they were three unspecified
consequences of having one, each now specified rather than avoided:

- Omission and `false` had to stop being synonyms, so absence can reach the
  settings tier.
- A user-scope default follows the user into workspaces where worktree preflight
  hard-fails, which is why an inherited mode degrades and an authored mode does
  not.
- `named` as a workspace-wide default serializes execution through one exclusive
  lease. It is permitted, but warned about at both the settings row and the
  drawer.

### Branch prefix as ownership → durable Git-admin ownership records

Names are conventions, not deletion authority. A durable record survives
directory removal and makes cleanup and crash recovery safe.
